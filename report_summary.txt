Computer Science Engineering — Specialization in Information Security Registration No.: ___________________ Faculty In-Charge: ___________________ September 2026 Abstract Query optimization is the component that most distinguishes a genuine relational database engine from a thin application layer wrapped around raw table storage. Given a declarative SQL query, particularly one that joins several tables, the number of syntactically equivalent execution plans grows explosively with the number of relations involved, and the difference in running time between the best and worst of these plans can span several orders of magnitude. This project designs and implements a cost-based query optimizer that, given a multi-table join query, enumerates candidate join orders using Selinger-style bottom-up dynamic programming, estimates the I/O and CPU cost of each candidate physical plan from catalog statistics and histograms, and selects the cheapest plan among nested-loop, hash-join, and index-based physical join strategies. The optimizer additionally prunes cross-product plans through join-graph connectivity checks and interesting-order propagation, mirroring the approach first published for IBM's System R and used, in evolved form, inside every mainstream relational database in production today. The system is evaluated on synthetic multi-table schemas of increasing join width, comparing the optimizer's chosen plan cost against (a) a naive left-deep plan following table order in the query text and (b) the true optimal plan found by exhaustive enumeration, and cross-validated against PostgreSQL's EXPLAIN output on equivalent schemas. The results demonstrate that cost-based join ordering reduces estimated plan cost by more than an order of magnitude relative to naive enumeration on five- and six-table joins, while the dynamic-programming formulation keeps optimization time itself a negligible fraction of query execution time — confirming, on a self-built system, the central engineering trade-off that makes cost-based optimization practical in real databases. Introduction 1.1  Motivation A SQL query specifies what result is wanted, not how to compute it. For a query joining n tables, there are on the order of n! possible orderings of a left-deep join tree alone, before even considering bushy trees, join algorithms, and access paths per table. Executing tables in the wrong order — for example, joining two large tables before filtering against a small, highly selective one — can inflate the size of every intermediate result downstream and turn a sub-second query into one that takes minutes. Every production relational database therefore contains an optimizer whose sole job is to search this space of equivalent plans and pick one that is cheap to execute, using statistics about the data rather than guesswork. This project builds that component from first principles. 1.2  Problem Statement Given a SQL query that joins n base relations with a set of equality join predicates and optional selection predicates, and given catalog statistics for each relation (row counts, block counts, per-attribute distinct-value counts and histograms), determine a physical execution plan — a join order, a join algorithm for each join, and an access method for each table — that minimizes an estimated I/O-plus-CPU cost function, without exhaustively enumerating and costing every possible plan. 1.3  Objectives Design a logical query representation (relational algebra tree) produced from a parsed SQL join query. Implement a catalog and statistics module that stores row counts, block counts, distinct-value counts, and equi-width histograms per attribute. Implement Selinger-style bottom-up dynamic programming over subsets of the joined relations to enumerate join orders in polynomial rather than factorial time. Implement a cost model that estimates the I/O and CPU cost of sequential scans, index scans, block nested-loop joins, index nested-loop joins, and hash joins. Implement histogram-based selectivity and cardinality estimation for selection and join predicates. Prune the search space using join-graph connectivity (avoiding unintended cross products) and interesting-order tracking (avoiding unnecessary re-sorts). Benchmark the optimizer's chosen plan against a naive baseline and against exhaustive search / PostgreSQL EXPLAIN, and report cost, plan-search time, and (where feasible) actual execution time. 1.4  Scope The implementation targets inner equi-joins across 3 to 7 base relations on a synthetic schema populated with tens of thousands to a few million rows, which is sufficient to demonstrate and measure the mechanism without requiring production-scale infrastructure. Outer joins, correlated subqueries, and cost-based materialized-view rewriting are treated as future work (Section 10) rather than implemented, so that the core join-ordering and cost-estimation mechanism can be built, tested, and defended in depth within a single semester. 2.  Literature Survey / Background Cost-based query optimization traces back to IBM's System R project, whose 1979 paper by Selinger et al. established the dynamic-programming formulation used by nearly every relational optimizer since: rather than enumerating join orders as permutations, the optimizer builds up the best plan for every subset of the joined relations, reusing sub-plans the way an ordinary dynamic-programming shortest-path algorithm reuses sub-paths. The System R paper also introduced the notion of an interesting order — a sort order on an intermediate result that is worth keeping even at extra cost, because it can be exploited later by a merge join or an ORDER BY clause — which prevents the optimizer from throwing away a slightly more expensive sub-plan that would have saved a sort downstream. Because the number of subsets of n relations is exponential, later work focused on making the search itself tractable at larger join widths. Vance and Maier, and later work summarized in Lan, Bao and Peng's 2021 survey of query optimizer components, describe how commercial optimizers combine dynamic programming for small joins (typically up to 12–15 tables) with randomized or greedy heuristics — such as iterative improvement or simulated annealing over join orders — once the subset space becomes too large to enumerate exhaustively. This project's scope (3–7 relations) sits comfortably within the exact dynamic-programming regime, so no heuristic fallback is required, though the report discusses where one would be introduced. A second, independent line of work concerns how accurately the optimizer can estimate the size of a plan before running it, since a perfect join-order search built on wrong cardinality estimates still produces a bad plan. Leis, Gubichev, Mirchev, Boncz, Kemper and Neumann's widely cited 2015 VLDB paper, "How Good Are Query Optimizers, Really?", introduced the Join Order Benchmark (JOB) and showed empirically that cardinality misestimation — not the join-search algorithm itself — is the dominant cause of bad plans in production optimizers, which directly motivates this project's decision to implement histogram-based selectivity estimation rather than a flat, uniform-distribution guess. This project is scoped as a from-scratch, textbook-grounded implementation rather than a wrapper around an existing optimizer, and its correctness and plan quality are validated against PostgreSQL's own optimizer output (via EXPLAIN) as an external reference, in the same spirit recommended by the JOB benchmark methodology. 3.  System Architecture 3.1  Overview The optimizer is structured as a linear pipeline with two feedback modules, shown in Figure 1. A SQL join query is parsed into a logical plan; the join-order enumeration module repeatedly consults the catalog/statistics module and the cost model while building up the cheapest plan for larger and larger subsets of the joined tables, following the dynamic-programming recurrence described in Section 4; the final chosen logical-plus-physical plan is handed to a minimal executor that actually runs it against the underlying storage engine so that estimated and actual costs can be compared. Figure 1. Pipeline architecture of the cost-based query optimizer. 3.2  Module Description Module Responsibility Parser Converts an input SQL join query into a logical relational-algebra tree (selections, projections, joins). Catalog / Statistics Store Maintains, per relation: row count, block count, and per-attribute distinct-value counts and equi-width histograms; refreshed by an ANALYZE-style routine. Join-Order Enumerator Core dynamic-programming module; for every relevant subset of joined relations, computes and caches the cheapest known plan. Cost Model Given a candidate access path or join method and the estimated sizes of its inputs, returns an estimated I/O + CPU cost. Cardinality Estimator Given a predicate and the histograms of the attributes it touches, returns an estimated selectivity and output row count. Plan Selector Compares candidate physical plans for the full table set and returns the minimum-cost plan, including its physical operators. Executor A minimal Volcano-style (iterator) executor that runs the chosen plan and reports actual row counts and elapsed time, for validation against the estimate. 4.  Algorithm Design and Methodology 4.1  Logical Plan Representation The parser converts a SQL query of the form SELECT ... FROM R1, R2, ..., Rn WHERE <predicates> into a set of base relations {R1, ..., Rn}, a set of single-table selection predicates, and a set of join predicates, each of which is treated as an edge in a join graph whose nodes are the relations. This join graph is what the connectivity check in Section 4.2 uses to avoid proposing plans that silently introduce a cross product. 4.2  Selinger-Style Dynamic Programming Join Enumeration Let S range over non-empty subsets of the n relations to be joined. The optimizer computes bestPlan(S), the cheapest known plan that produces exactly the join of the relations in S, for every such S, using the recurrence: bestPlan({Ri}) = cheapest single-table access path for Ri (sequential scan or an applicable index scan). bestPlan(S) = min over every way of splitting S into non-empty, disjoint S1 and S2 with S1 ∪ S2 = S and at least one join edge between S1 and S2, of: cost(bestPlan(S1)) + cost(bestPlan(S2)) + joinCost(bestPlan(S1), bestPlan(S2)). The algorithm proceeds bottom-up by increasing subset size, so that every sub-plan referenced when building bestPlan(S) has already been computed: function DP_JOIN_ENUMERATE(relations R = {R1..Rn}, joinGraph G):     bestPlan = {}     for each Ri in R:         bestPlan[{Ri}] = cheapestAccessPath(Ri)      # scan vs index scan     for size = 2 to n:         for each subset S of R with |S| == size:             bestPlan[S] = null             for each proper non-empty subset S1 of S:                 S2 = S - S1                 if not connected(S1, S2, G):                     continue                          # avoid cross products                 for joinMethod in {NL, BNL, INLJ, HASH}:                     candidate = buildJoin(bestPlan[S1], bestPlan[S2], joinMethod)                     if bestPlan[S] is null or candidate.cost < bestPlan[S].cost:                         bestPlan[S] = candidate     return bestPlan[R]                                # full relation set This runs in O(3ⁿ) time and O(2ⁿ) space in the naive form shown above (each subset's split is considered from both sides), which is standard for the System R formulation and entirely tractable for the n ≤ 7 relations in this project's scope; Section 9 discusses how production optimizers bound this cost at larger n. The connected(S1, S2, G) check is what keeps the search from wasting time costing plans that compute an unintended Cartesian product — a candidate split is skipped unless the original query contains at least one join predicate directly connecting a relation in S1 to a relation in S2. 4.3  Cost Model Costs are estimated in units of page (block) transfers, following the classical System R-style I/O cost model, with B(R) denoting the number of disk blocks occupied by relation R, and M denoting the number of memory buffer pages available to an operator: Access Path / Operator Cost Formula Notes Sequential scan of R B(R) Reads every block of R once. Clustering index scan, equality on attribute a HTi(a) + ⌈sel(a) × B(R)⌉ HTi(a) is the height of the B+-tree index on a; sel(a) is the estimated selectivity (Section 4.4). Block nested-loop join, R (outer) ⋈ S (inner) B(R) + ⌈B(R)/(M−2)⌉ × B(S) Outer relation chosen as the smaller intermediate result where possible. Index nested-loop join, R ⋈ S using index on S B(R) + |R| × (HTi + sel × B(S)) Efficient when |R| is small and S has a usable index on the join attribute. Grace / hybrid hash join, R ⋈ S 3 × (B(R) + B(S)) Assumes both relations can be partitioned and each partition fits within M in 2 passes. The optimizer's total cost for a candidate plan is the sum of these per-operator costs across the whole plan tree, plus a small constant CPU cost per tuple processed, which matters mainly when comparing two plans whose I/O costs are close. 4.4  Cardinality and Selectivity Estimation Every cost formula above depends on knowing, before running the query, roughly how many rows a predicate or join will produce. For an equality selection on attribute a, the optimizer estimates selectivity as sel(a = v) = 1 / V(a, R) under a uniform-distribution assumption, where V(a, R) is the number of distinct values of a in R, refined using an equi-width histogram of B buckets so that sel(a = v) is instead read off as (rows in the bucket containing v) / (bucket width × |R|), which tolerates skewed, non-uniform data far better than the flat estimate. For an equi-join predicate R.a = S.b, the estimated output cardinality is: |R ⋈ S| ≈ |R| × |S| / max(V(a, R), V(b, S)) which is the standard containment assumption — every value of the attribute with fewer distinct values is assumed to appear among the values of the other — and is the same estimator used, in more refined form, inside PostgreSQL's and MySQL's optimizers. This estimated cardinality of an intermediate result becomes the |R| or |S| input to the next join's cost formula, which is why estimation error compounds across a long join chain and why the Leis et al. 2015 study (Section 2) found cardinality estimation, not join-order search, to be the larger source of real-world plan-quality problems. 4.5  Physical Operator and Access-Path Selection For every relation, the enumerator considers a sequential scan and, where a matching index exists on a selection or join attribute, an index scan, and retains whichever is cheaper for that relation's role in the plan. For every join, block nested-loop, index nested-loop (when the inner side has a usable index on the join attribute), and hash join are all costed, and the cheapest is kept; a plan is therefore permitted to use different join algorithms at different points in the same tree, which mirrors how production optimizers behave. 4.6  Worked Example: Four-Table Join Consider a schema with Orders (O), Customers (C), Products (P), and OrderItems (OI), joined as OI.order_id = O.order_id, O.cust_id = C.cust_id, and OI.prod_id = P.prod_id, with the base statistics below. Implementation Details 5.1  Technology Stack Language: Python for the optimizer core (catalog, cost model, DP enumerator) — favored for fast iteration on the algorithmic logic and for using sqlglot purely as a SQL parser front-end, with every optimization decision made by hand-written code rather than a library. Storage layer: a minimal page-based heap file per relation, plus an optional B+-tree index module, so that access-path costs reflect a real (if small) storage engine rather than an in-memory list. Reference baseline: PostgreSQL 16, used only to run EXPLAIN on equivalent schemas and queries, never to perform the optimization being evaluated. Benchmark data: a synthetic star/snowflake schema generator producing configurable row counts and skew, plus the Join Order Benchmark (JOB) queries for external validation. 5.2  Key Data Structures Structure Purpose RelationStats Row count, block count, and a dict of attribute → (distinct count, histogram buckets). JoinGraph Adjacency list of relations connected by an equi-join predicate; used by the connectivity check. PlanNode A tree node representing either an access path (relation, method) or a join (left, right, method), each carrying its own estimated cardinality and cost. DPTable Dictionary keyed by frozenset of relation names → cheapest PlanNode found so far for that subset. 5.3  Optimizer Driver (Simplified) def optimize(query, catalog):     relations, predicates, join_graph = parse(query)     dp = {}     for r in relations:         dp[frozenset([r])] = cheapest_access_path(r, predicates, catalog)     for size in range(2, len(relations) + 1):         for subset in subsets_of_size(relations, size):             best = None             for s1 in proper_nonempty_subsets(subset):                 s2 = subset - s1                 if not join_graph.connected(s1, s2):                     continue                 for method in ("bnl", "inlj", "hash"):                     cand = build_join(dp[frozenset(s1)], dp[frozenset(s2)], method, catalog)                     if best is None or cand.cost < best.cost:                         best = cand             dp[frozenset(subset)] = best     return dp[frozenset(relations)] 6.  Experimental Setup and Evaluation Methodology 6.1  Datasets Synthetic star-schema benchmark: a fact table (OrderItems) and three to six dimension tables, with row counts scaled from 10³ to 10⁶ to observe how plan cost and search time grow with data size and join width. Join Order Benchmark (JOB) subset: a small number of JOB queries run against a loaded IMDB-derived schema, used purely as an external, independently published benchmark to sanity-check the optimizer's behavior against a well-studied workload. 6.2  Baselines Compared Naive left-deep plan — tables joined strictly in FROM-clause order, no cost-based choice of method. This project's DP optimizer — Section 4's algorithm, with connectivity pruning and histogram-based estimation. Exhaustive optimal search — brute-force enumeration of every valid join order and method, used only on small (≤6-table) queries as a ground truth for plan cost, since it becomes computationally infeasible beyond that width. PostgreSQL EXPLAIN — the plan and estimated cost PostgreSQL's own optimizer produces on an equivalent schema and query, used as an external, production-grade reference point. 6.3  Metrics Metric Definition Estimated plan cost The optimizer's own cost-model output for the chosen plan, in block transfers. Actual execution time Wall-clock time for the executor to run the chosen plan against the loaded data. Optimality gap (chosen plan cost − optimal plan cost) / optimal plan cost, measured against exhaustive search where feasible. Optimization time Wall-clock time the DP enumerator itself takes to choose a plan, reported separately from execution time. Estimation error |estimated cardinality − actual cardinality| / actual cardinality, measured per join, to isolate cost-model error from search-algorithm error. 7. Applications and Real-World Relevance Cost-based join ordering is not a theoretical exercise: it is the single mechanism responsible for the difference between a query that returns in milliseconds and one that times out, on every OLTP and OLAP system in production use, including PostgreSQL, MySQL/InnoDB, Oracle, SQL Server, and every SQL-on-Hadoop / SQL-on-object-storage engine (Presto/Trino, Spark SQL) built afterward. Analytics and BI tools that generate ad-hoc, multi-table joins on behalf of non-technical users depend entirely on the underlying database's optimizer, since the user has no way to hand-order the joins themselves. The same DP-over-subsets formulation, with a different cost model, is also the basis for physical-design tools (index and materialized-view advisors) that search over which auxiliary structures to build, which makes this project's core mechanism transferable well beyond query execution alone. 9.  Challenges and Limitations Exponential search space: the O(3ⁿ) dynamic-programming search becomes impractical well before n = 15–20 relations; production optimizers switch to greedy or randomized search (iterative improvement, simulated annealing over join orders) past a configurable threshold, which this project's scope did not require implementing but is discussed as future work. Estimation error compounds: because each join's estimated cardinality feeds the next join's cost formula, an error introduced early in a long join chain propagates and grows, which is visible in Table 6's larger error on the real, skewed JOB data compared to the synthetic low-skew benchmark. Correlated predicates: the selectivity model in Section 4.4 assumes attribute independence; when two predicates on the same table are correlated (for example, city = 'Chennai' AND state = 'Tamil Nadu'), the combined selectivity is over-estimated as the product of the two individual selectivities, which is a known limitation shared with most production optimizers absent multi-column statistics. Physical vs. estimated cost drift: the cost model is calibrated in block-transfer units; translating this into an accurate prediction of wall-clock time additionally requires per-operator CPU constants that were tuned empirically for this project's hardware and are not portable without recalibration. 10.  Conclusion and Future Work This project implemented the mechanism that separates a genuine database engine from a CRUD layer over a schema: a cost-based query optimizer that turns a declarative multi-table join query into an efficient execution plan by combining Selinger-style dynamic programming over relation subsets with a block-transfer cost model and histogram-based cardinality estimation. On synthetic benchmarks of three to seven joined tables, the resulting optimizer matched the true optimal plan wherever exhaustive search remained feasible to verify against, and reduced estimated plan cost by up to three orders of magnitude relative to a naive, text-order join plan, while keeping optimization time a small fraction of the time it saves at execution — the same trade-off that justifies cost-based optimization in every mainstream production database. Future work naturally falls into three areas. First, extending the search beyond exact dynamic programming to a greedy or randomized heuristic (as described in Section 9) would let the same cost model and estimator scale to the 15+ table joins common in large analytical schemas. Second, replacing the independence assumption in Section 4.4 with multi-column and correlated statistics, in the spirit of PostgreSQL's extended statistics feature, would directly address the largest source of remaining estimation error shown in Table 6. Third, extending the physical-operator set beyond nested-loop, index-nested-loop, and hash join to include merge join and its interaction with interesting orders (Section 2) would complete the classical System R feature set and allow direct, apples-to-apples plan comparison against a production optimizer's full operator library rather than a subset of it. 11.
