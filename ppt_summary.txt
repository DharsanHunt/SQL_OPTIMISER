01 MOTIVATION & PROBLEM Why Join Ordering Matters n! possible left-deep join orders for an n-table query The wrong join order can inflate intermediate results and turn a sub-second query into one that  times out. Every production RDBMS — PostgreSQL, MySQL, Oracle, SQL Server — carries a cost-based optimizer for exactly this reason. PROBLEM STATEMENT Given a SQL query joining n base relations with equality join predicates, and catalog statistics for each relation (row counts, block counts, distinct-value counts, histograms), determine an execution plan — join order, join algorithm, and access method per table — that minimizes estimated I/O + CPU cost, without exhaustively enumerating every plan. Given:   relations, join graph, statistics Find:   minimum-cost join order + physical plan Constraint:   polynomial-time search, not brute force COST-BASED QUERY OPTIMIZER  ·  REVIEW 1 03

05 METHODOLOGY Selinger-Style Join-Order Enumeration THE RECURRENCE bestPlan({Ri}) = cheapest single-table access path
 bestPlan(S) = min split (S1, S2) of:    cost(S1) + cost(S2) + joinCost(S1, S2) HOW IT'S BUILT 1 Bottom-up over subset size: singles → pairs → triples → ... 2 Each subset reuses the best sub-plans already computed 3 Join-graph connectivity check skips unintended cross products 4 Every join costed as block-nested-loop, index-NL, and hash join SEARCH COMPLEXITY O(3ⁿ) time, O(2ⁿ) space Exact for the project's scope of 3–7 joined relations — exhaustive but tractable, unlike n! plan permutations. WHY CONNECTIVITY PRUNING MATTERS On a 4-table worked example, a plan forced into a cross product cost ≈ 812,000 block transfers — the connectivity-pruned, cost-based plan cost ≈ 14,900. 06 COST MODEL Cost Model & Cardinality Estimation Operator Cost Formula Sequential scan of R B(R) Index scan (equality) HTi + sel × B(R) Block nested-loop join B(R) + ⌈B(R)/(M−2)⌉ × B(S) Hash join 3 × (B(R) + B(S)) JOIN CARDINALITY ESTIMATE |R ⋈ S| ≈ |R| × |S| / max(V(a,R), V(b,S)) Selectivity refined further with equi-width histograms per attribute, rather than a flat uniform-distribution guess. WHY THIS MATTERS A cost-based search is only as good as its cardinality estimates — Leis et al. (2015) found estimation error, not the join-order search itself, to be the larger source of bad plans in production optimizers. This project implements both halves of the problem.
